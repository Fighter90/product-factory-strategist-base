# Быстрый MVP в Data Science — сборка на API, автоматизации и low-code

## Когда применять
Гипотеза сформулирована ([[M-mvp-pilots]]) и нужно собрать первую проверяемую версию продукта за дни, а не месяцы: силами одного продакта/аналитика или маленькой команды, без полноценной разработки. Типовые случаи: сервис поверх LLM по API, автоматизация рутинного процесса, «умная» обработка документов/текстов. Карта — про конвейер сборки и выбор стека, не про выбор типа MVP.

## Суть
**Быстрый MVP — это не «недоделанный продукт», а полный минимальный конвейер одной задачи:** вход (данные/запрос пользователя) → обработка (модель по API / правила / скрипт) → выход (результат + фиксация ответа) → обратная связь (что пользователь считает хорошим ответом). Всё, что не входит в проверяемую гипотезу, — вырезается: без регистраций, биллинга, админок, дизайна.

**Три стека сборки — выбирать по требуемой скорости и где живёт решение:**
| Стек | Что это | Когда выбирать | Ограничения |
|---|---|---|---|
| Код + API (Python/JS) | скрипт/бэкенд, вызовы моделей и сервисов по API | нужна логика/данные, контроль качества, шаг к продакту | нужны навыки программирования |
| Workflow-автоматизация (визуальные no-code конвейеры) | узлы-шаги: триггер → запрос → модель → действие | процессы и интеграции «склеить без кода», автоматизация рутины, демонстрация MVP за часы | сложная логика и масштабирование упираются в потолок; стоимость растёт с числом запусков |
| Low-code конструкторы | готовые интерфейсы/боты поверх форм | нужен UI для пользователя «из коробки», демонстрация концепции | минимальная кастомизация, привязка к платформе |

Стеки комбинируются: типовой MVP = low-code интерфейс (или чат-бот) + workflow-конвейер + модели по API + таблица/база для хранения ответов.

**LLM-часть MVP (когда ядро — модель):** чётко разделить системный промпт (роль, правила, формат ответа) и пользовательские данные; фиксировать примеры входа/выхода до сборки; измерять качество на мини-наборе тестовых случаев, а не «на глаз» ([[M-genai-evals]]); для поиска по документам — схема RAG (получить релевантные фрагменты → вставить в промпт), а не «отдать весь документ». Архитектурные варианты ассистентов — [[M-genai-assistant-architecture]], проектирование GenAI-прототипа — [[M-genai-prototyping]].

**Что отличает MVP от демо:** повторяемость (работает у пользователя без вас), фиксация данных (каждый запуск записан: вход, выход, оценка), измерение (метрика проверки из гипотезы), ограниченная честность (декларировать, что данные не накапливаются в прод-качестве, лимиты). Демо без фиксации данных не проверяет гипотезу — его не с чем анализировать.

**Работа с API — минимум продакта:** ключи не в коде (переменные окружения/секреты), повтор при сетевых ошибках и тайм-ауты, контроль лимитов и стоимости вызовов (счётчик токенов/запусков), логирование ошибок. Для workflow-конвейеров то же самое — настройки узлов: retry, timeout, лимит очереди.

**Правило времени сборки:** если MVP не собирается за 1–2 недели — скоуп всё ещё не минимален; урезать задачу, а не «строить быстрее».

## Процедура
1. **Выписать проверяемую гипотезу и метрику** ([[M-hypothesis-testing]], [[M-mvp-pilots]]): что должно случиться с метрикой у первых пользователей, чтобы продолжать.
2. **Определить минимальный конвейер одной задачи:** вход → обработка → выход → фиксация; всё остальное — в список «не в MVP» письменно (защита от расползания скоупа).
3. **Выбрать стек** по таблице: скорость vs контроль; записать допущение («для проверки гипотезы достаточно low-code; при подтверждении переписываем на код»).
4. **Спроектировать модельную часть (если есть):** системный промпт, 10–20 тестовых входов с ожидаемым выходом, порог качества (доля хороших ответов), схема RAG при поиске по документам.
5. **Собрать конвейер:** интерфейс (low-code/бот/минимальная форма) → workflow/скрипт → вызовы API → хранение ответов (таблица: timestamp, вход, выход, оценка пользователя, сегмент).
6. **Обвязка продакта-минимума:** секреты вне кода, retry/тайм-ауты, счётчик стоимости вызовов, журнал ошибок.
7. **Протестировать самому как злой пользователь:** 5–10 прогонов типовых и граничных случаев (пустой вход, длинный документ, вопрос не по теме); починить критичное.
8. **Прогнать мини-юзабилити** на 3–5 целевых пользователях ([[M-usability-testing]]): проходят ли сценарий без вас; собрать первые оценки качества ответов.
9. **Отдать узкому кругу пользователей с фиксацией:** все запуски в таблице; явно попросить оценку каждого результата (👍/👎 + комментарий) — это будущий датасет качества.
10. **Свести проверку гипотезы:** метрика из шага 1 на фактических данных; решения: продолжать/переделать ядро/закрыть; для LLM-ядра — частые категории ошибок → правки промпта/данных ([[M-genai-evals]]).
11. **План после сигнала:** подтверждение → дизайн полноценной версии (стек может смениться); опровержение → разбор причины (продукт? качество модели? задача не болит?).

## Типичные ошибки
- Строить два месяца «MVP» с биллингом, регистрацией и админкой — это не проверка гипотезы, а продукт без валидации.
- Демо вместо MVP: показывается один раз автором, запуски не фиксируются, анализировать нечего.
- Промпт «на глаз»: нет тестовых случаев и порога качества, каждое изменение ломает неизвестно что.
- Ключи API в коде/репозитории; отсутствие тайм-аутов и счётчика стоимости — первый же spike трафика сжигает бюджет.
- RAG как «вставь весь документ в промпт»: длинный контекст дороже и хуже по качеству, чем подобранные фрагменты.
- Сложить MVP на low-code и не записать допущение о переписывании: потолок платформы находят на реальном трафике.
- Замерять качество «у меня работает»: без оценок пользователей сигнал о качестве отсутствует.

## Вопросы, которые могут изменить решение
- Какая одна задача вырезается из конвейера без потери проверяемости гипотезы?
- Достаточно ли low-code/workflow для этой гипотезы — или логика уже требует кода?
- Каков порог качества ответов модели, ниже которого продукт вредит (и как его измерить на 20 случаях)?
- Сколько стоит один запуск конвейера и какой бюджет на пилот?
- Что запишем о каждом запуске, чтобы через неделю ответить «работает или нет»?
- Если гипотеза подтвердится — какой стек в полноценной версии и что из MVP переживёт миграцию?
