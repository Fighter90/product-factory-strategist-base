# Проверка продуктовых гипотез в B2B — специфика, риски, приёмы

## Когда применять
Продукт продаётся компаниям, а не частным лицам, и нужно проверить проблемную, ценностную или монетизационную гипотезу. Стандартные B2C-приёмы (A/B на большом трафике, массовые опросы) часто неприменимы: база мала, доступ к клиентам через людей, решения принимают несколько ролей. Карта — что меняется в проверке и как не обмануть себя.

## Суть
**B2B ≠ B2C в масштабе данных, а не в логике проверки.** Логика одна: гипотеза → данные, способные её опровергнуть → решение ([[M-hypothesis-testing]]). Меняются условия: популяция — десятки–сотни компаний вместо миллионов пользователей; каждый респондент — самостоятельная ценность; доступ — через контакты и переговоры; решение о покупке — групповое и длинное.

### Четыре структурные особенности B2B
1. **Малая популяция.** Рынок из 200 компаний не даёт статистической значимости в классическом смысле. Компенсация: глубокое качественное исследование каждой компании, экспертные оценки, количественные проверки на внутрикомпанных данных (пользователей у одного клиента много), последовательные пилоты вместо параллельных A/B.
2. **Цепочка ролей.** Пользователь (тот, кто работает с продуктом) ≠ заказчик (тот, кто платит) ≠ ЛПР (тот, кто решает) ≠ блокирующий (тот, кто может запретить). Боль пользователя реальна, но гипотезу о покупке проверяют у заказчика и ЛПР: у каждого своя задача («работать быстрее» у пользователя; «снизить издержки/риск, объяснить руководству» у заказчика).
3. **Длинный и лощечный цикл сделки.** Решение занимает месяцы, зависит от бюджета сезона и истории отношений. «Горячий интерес» на интервью часто не превращается в договор: ждать факта платежа, а не энтузиазма.
4. **Персонализация сделки.** Каждый клиент просит «небольшую доработку»: легко принять wish клиента за спрос рынка. Один довольный якорный клиент с индивидуальной конфигурацией — не доказательство ценностной гипотезы для сегмента.

### Специфика рисков проверки
| Риск | Как выглядит | Приём |
|---|---|---|
| Смещение выборки | интервью с дружественными клиентами, с которыми уже есть контакт | план выборки по сегментам, включая «холодные» и ушедших клиентов |
| Голос не тех ролей | боль пользователя принимают за готовность платить | карта ролей сделки; отдельные вопросы для пользователя/заказчика/ЛПР |
| Вежливость вместо истины | «интересно, вышлите презентацию» читается как спрос | считать доказательством только ресурсы: время, данные, деньги, люди |
| Wish ≠ спрос | «сделайте вот эту галочку — купим» (не купят) | проверять готовность платить на текущей версии, а не обещания |
| Ложная генерализация | один якорный клиент = «весь сегмент так себя ведёт» | минимальный порог: 3–5 компаний из разных сегментов до вывода о сегменте |
| Утечка фокуса | пилот затягивается доработками под клиента, гипотеза уже не проверить | границы пилота фиксируются до старта: объём, срок, критерий успеха |

**Доказательства, которым можно верить в B2B (по убыванию силы):** факт платежа/подписанного договора; использование продукта в рабочем процессе после пилота (логи активности); готовность предоставить данные/людей для интеграции; подробно описанный процесс «как решаем задачу сейчас» с цифрами; заявление о готовности платить (самое слабое).

## Процедура
1. **Разложить гипотезу по ролям:** пользователь/заказчик/ЛПР/блокирующий — что каждая роль должна подтвердить для успеха; карта интересов и рисков сделки.
2. **Составить план выборки по сегментам:** какие типы компаний обязательны (размер, отрасль, зрелость процесса), сколько компаний на сегмент (минимум 3–5 для качественных выводов), включая труднодоступных и «ушедших».
3. **Провести проблемные интервью по ролям:** у пользователя — текущий процесс, частота, цена ошибки; у заказчика — бюджетный процесс, кто и как принимает решение, что нужно для внутреннего согласования ([[M-in-depth-interviews]]). Искать факты процесса и деньги, не мнения о продукте.
4. **Проверить ценность на подступах к платежу:** демонстрация на данных клиента; письмо-предложение с ценой и объёмом; предпилотное соглашение: клиент даёт данные и время, вы даёте результат. Доказательство — выделенные ресурсы клиента.
5. **Спроектировать пилот с границами до старта:** объём (что входит/не входит), срок, критерий успеха (конкретная метрика на данных клиента), кто подписывает результат. Пилот без критерия успеха = бесконечная доработка.
6. **Фиксировать сигналы по каждой компании одинаково** (шаблон: сегмент, роли, боль с частотой, процесс сейчас, реакция на предложение, выделенные ресурсы, решение) — для сравнения, а не разрозненных историй.
7. **Свести по сегментам:** подтвердилась ли гипотеза в каждом; где границы применимости вывода; считается ли один якорный клиент исключением или правилом.
8. **Принять решение с учётом цикла сделки:** прогноз выручки строить по воронке с длительностями стадий, а не по «тёплым» контактам; заложить сезонность бюджетов.

## Шаблон / чек-лист
| Поле | Заполнить |
|---|---|
| Гипотеза и роли (кто должен подтвердить) | пользователь / заказчик / ЛПР / блокирующий |
| Сегменты и план выборки | типы компаний, минимум по 3–5 на сегмент |
| Процесс решения у клиента | кто, как, по какому бюджетному циклу |
| Критерии доказательства | платежи / ресурсы / логи пилота / слова |
| Границы пилота | объём, срок, критерий успеха, ответственный |
| Сигналы по компаниям | единый шаблон, сравнение по сегментам |
| Прогноз сделки | воронка, длительность стадий, сезонность |

## Критерии качества
- Гипотеза разложена по ролям сделки (пользователь / заказчик / ЛПР / блокирующий); монетизационная проверена у платящей роли.
- План выборки по сегментам выполнен: 3–5 компаний на сегмент, включая «холодные» и ушедшие, а не только дружественные.
- Доказательства — ресурсы клиента (деньги, время, данные, люди), а не заявления об интересе.
- Пилот имеет границы до старта: объём, срок, критерий успеха на данных клиента, кто подписывает результат.
- Сигналы по компаниям собраны в едином шаблоне и сведены по сегментам; вывод о сегменте не построен на одном якорном клиенте.
- Прогноз сделки учитывает длину цикла и бюджетный календарь, а не «тёплые» контакты.

## Типичные ошибки
- Проверять гипотезу о покупке у пользователя, а не у заказчика/ЛПР.
- Считать «интересно, давайте презентацию» доказательством спроса; доказательство — ресурсы клиента (деньги, время, данные, люди).
- Строить выводы о сегменте на одном якорном клиенте с индивидуальной конфигурацией.
- Опрашивать только дружественные компании; не включать ушедших и «холодных».
- Пилот без заранее зафиксированного критерия успеха — превращается в бесплатный аутстафф.
- Переносить B2C-логику: ждать статистической значимости, которой не может быть на популяции из 200 компаний.

## Вопросы, которые могут изменить решение
- Кто подписывает договор и что нужно каждому звену цепочки, чтобы подписать?
- Сколько компаний сегмента уже подтвердили боль фактом процесса (не словами)?
- Готов ли хоть один клиент платить на текущей, неидеальной версии?
- Каков реальный бюджетный цикл: попадёт ли пилот в окно закупок?
- Что если якорный клиент — исключение: кто в сегменте «средний», и проверяли ли его?
