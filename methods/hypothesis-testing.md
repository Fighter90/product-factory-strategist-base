# Выбор метода проверки продуктовой гипотезы

## Когда применять
Сформулирована продуктовая гипотеза и встаёт вопрос «как её проверить?»: какой метод исследования или эксперимента выбрать, сколько это стоит по времени и деньгам, какие риски несёт сам выбор метода. Карта — процедура выбора: от типа гипотезы и цены ошибки решения к минимально достаточному методу.

## Суть
**Гипотеза — не вопрос, а проверяемое утверждение.** Продуктовая гипотеза связывает действие с ожидаемым изменением метрики: «если сделаем X, то Y изменится на Z для сегмента W, потому что …». Проверка = сбор таких данных, которые могут опровергнуть гипотезу и изменить решение. Если данные не могут изменить решение — это не исследование, а ритуал.

**Метод выбирает не «как принято», а под три вещи:**
1. **Тип гипотезы.** Проблемная («у сегмента есть боль»), ценностная («решение снимает боль»), юзабилити («пользователь сможет пройти сценарий»), канальная (канал приводит нужных пользователей), монетизационная («готовы платить столько-то»), роста (механика даёт инкремент).
2. **Цена ошибки решения.** Сколько потеряем, если ошибёмся: обратимое решение (кнопку можно убрать) допускает быстрый дешёвый метод; необратимое (закрыть направление, изменить монетизацию) требует сильных доказательств.
3. **Доступ к данным и респондентам.** Есть ли база пользователей, возможность A/B, доступ к ЛПР в B2B (см. [[M-b2b-validation]]), готовность платить за выборку.

### Карта «тип гипотезы → методы»
| Тип гипотезы | Быстро и дёшево | Дороже, но сильнее |
|---|---|---|
| Проблемная | проблемные интервью, наблюдение, партизанское исследование ([[M-guerrilla-research]]) | количественный опрос на репрезентативной выборке ([[M-quant-methods]]), анализ логов поиска спроса |
| Ценностная | кликабельный прототип, «поддельная дверь» (фейковый тариф на лендинге) | A/B-тест ценности, пилот с якорными клиентами |
| Юзабилити | тест на 5 респондентах ([[M-usability-testing]]) | модерируемый тест на целевых сегментах, сравнение с конкурентом |
| Канальная | малые платные тесты канала, CPL-замер | масштабный тест с контролем качества трафика |
| Монетизационная | опрос о готовности платить, Van Westendorp ([[M-van-westendorp]]) | A/B по цене, предзаказы, продажа до сборки |
| Роста / инкремент | прогноз и каннибализация в модели ([[M-traction-model]], [[M-cannibalization]]) | A/B-тест с расчётом MDE ([[M-ab-testing]]) |

### Риски самого метода
- **Метод не отвечает на вопрос.** Опрос «купили бы вы…?» не проверяет монетизационную гипотезу (заявленное ≠ платёжное поведение); юзабилити-тест не проверяет спрос.
- **Метод со встроенным смещением.** Опрос по базе лояльных клиентов подтверждает что угодно; интервью с коллегами вместо пользователей; A/B на сегменте, котором не коснётся раскатка.
- **Дешёвый метод для дорогого решения.** Экономия на исследовании при необратимом решении — самый дорогой вид экономии.
- **Дорогой метод для дешёвого решения.** Полномасштабное исследование перед изменением подписи на кнопке.
- **Подтверждающий дизайн.** Исследование спроектировано так, что не может опровергнуть гипотезу (вопросы-подсказки, выборка «своих», отсутствие контрольной группы).

**Минимально достаточный метод** — самый дешёвый из тех, что способны изменить решение при любом исходе. Сначала «дешёвые опровержители» (интервью, прототип, логи), затем дорогие (опрос на выборке, A/B). Принцип: **скорость обучения за рубль**, а не «строгость ради строгости» (см. [[M-evidence-design]]).

## Процедура
1. **Переписать гипотезу в проверяемой форме:** что делаем, для кого, что ожидаем увидеть в конкретной метрике, за какой срок, почему (механизм). Тест: какие данные заставят признать «нет»?
2. **Оценить цену ошибки:** обратимое ли решение, сколько стоит месяц ложного пути, что сломается при ошибочном раскате. Цена ошибки определяет требуемую силу доказательств, а она — выбор метода.
3. **Перечислить 2–3 кандидата-метода** по карте «тип гипотезы → методы»; для каждого: что именно докажет или опровергнет, срок, стоимость, доступ к респондентам.
4. **Проверить каждого кандидата на риск метода:** может ли он ответить «нет»? где смещение выборки? что будет считаться успехом заранее (порог, MDE)?
5. **Выбрать минимально достаточный:** самый дешёвый из валидных. Если сомнение между качественным и количественным — сначала качественное (найти и понять механизм), затем количественное (измерить распространённость).
6. **Спроектировать проверку до сбора:** вопросы/сценарий/метрики, критерий успеха и провала, размер выборки, кто и когда принимает решение по результату. Зафиксировать письменно ([[M-brief-hypotheses]]).
7. **Провести, собрать сырые данные** (не только агрегаты): цитаты, ответы, логи — для аудита выводов.
8. **Свести вывод:** подтверждена / опровергнута / не проверена (метод не дал ответа); сила доказательств; что с решением. Опровергнутая гипотеза — такой же ценный результат; «не проверена» вернуться на шаг 3.

## Шаблон / чек-лист
| Поле | Заполнить |
|---|---|
| Гипотеза (в проверяемой форме) | если … то … для … потому что … |
| Тип гипотезы | проблемная / ценностная / юзабилити / канальная / монетизационная / роста |
| Цена ошибки решения | обратимо / необратимо; стоимость месяца ложного пути |
| Кандидаты-методы (2–3) | что докажет/опровергнет, срок, стоимость |
| Смещение выборки выбранного метода | кого не услышим |
| Критерий успеха заранее | метрика + порог + срок |
| Критерий провала заранее | что считается «нет» |
| Кто принимает решение по результату | роль, срок |

## Типичные ошибки
- Проверять монетизационную гипотезу вопросом «вы бы платили?» вместо теста платежа.
- Начинать с дорогого метода (полный опрос, A/B на большом трафике), когда ответ может дать 5 интервью за день.
- Не фиксировать критерий успеха до запуска — «в любом результате найдём подтверждение».
- Игнорировать смещение выборки: опрашивать доступных вместо целевых.
- Исследование без решения на выходе: собраны данные, но непонятно, что менять.
- Считать один метод достаточным для необратимого решения ([[M-evidence-design]] — триангуляция).

## Вопросы, которые могут изменить решение
- Какие данные заставят нас сказать «мы ошибались»? Если никаких — гипотеза не проверяема.
- Сколько стоит месяц движения в ложном направлении? Не мало ли мы тратим на проверку?
- Кто из респондентов недоступен выбранному методу, и как это смещает вывод?
- Можно ли проверить гипотезу «поддельной дверью» за неделю вместо полноценной сборки?
- Уже есть ли в логах/отчётах данные, которые опровергают или подтверждают гипотезу, прежде чем собирать новые?
