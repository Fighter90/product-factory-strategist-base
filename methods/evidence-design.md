# Дизайн доказательств — сколько и каких данных нужно для решения

## Когда применять
Перед дорогостоящим или необратимым решением: нужно заранее решить, какими доказательствами оно будет обосновано, сколько их достаточно и какого качества. Также — когда результат исследования «на грани» и надо понять, можно ли на нём решать. Карта закрывает вопрос «сколько данных хватит», а не «как собрать данные» (методы — [[M-hypothesis-testing]]).

## Суть
**Доказательство — данные, которые способны изменить решение.** Дизайн доказательств — это проектирование комплекта доказательств под решение: заранее определить, что будет считаться достаточным основанием, из каких источников и методов собирать, какие комбинации делают вывод устойчивым.

**Три вопроса дизайна доказательств:**
1. **Достаточность:** какой минимальный комплект данных позволяет принять решение? Недобор — решение на вере; перебор — потерянные недели и «паралич анализа».
2. **Качество (сила):** насколько данным можно верить. Шкала силы: прямое измерение поведения (платежи, логи, A/B) > структурированный самоотчёт (опросы, дневники) > интервью и наблюдение > экспертное мнение > аналогия/анекдот. Для источников — отдельная шкала A–D ([[M-source-criticism]]). Вывод не сильнее самого слабого критичного входа.
3. **Независимость (триангуляция):** доказательства из разных методов, на разных данных и выборках. Триангуляция повышает уверенность, только если входы независимы: два опроса одной базой — это один вход, а не два.

### Виды доказательств по отношению к гипотезе
| Вид | Что это | Пример | Риск |
|---|---|---|---|
| Прямое | данные о самом поведении/эффекте | A/B-тест конверсии, платежи, логи | дорого, нужны условия для теста |
| Косвенное | прокси-метрика, связанная с эффектом | клики по «поддельной двери», engagement прототипа | прокси может оторваться от целевой метрики |
| Свидетельское | слова пользователей | интервью, опросы, жалобы поддержки | разрыв между «говорят» и «делают» |
| Контекстное | внешние данные о рынке/аналогах | отчёты, бенчмарки конкурентов, история отрасли | чужой контекст ≠ наш |

**Правило комплектования:** чем дороже и необратимее решение, тем больше в комплекте должно быть прямых доказательств; свидетельские и косвенные — для поиска механизма и ранних сигналов, не для финального «да».

### Достаточность: критерий «стоп»
Заранее фиксируются: порог метрики (что считаем успехом), размер выборки/MDE ([[M-ab-testing]]), число независимых входов (обычно ≥ 2 для необратимых решений), кто признаёт комплект достаточным. Достаточность достигнута → решение принимается даже если «хотелось бы ещё проверить»; не достигнута → решение не принимается или переносится, а не «принимается со скрипом».

**Уверенность vs доказанность.** Цель — не абсолютная истина, а уверенность, достаточная для действия: у обратимых решений планка ниже (действуем и учимся), у необратимых — выше (сначала сильный комплект). Явно назвать уровень уверенности в документе решения: «подтверждено A/B и платежами» ≠ «подтверждено тремя интервью».

**Отрицательное доказательство ценнее подтверждающего:** ищите данные, которые опровергнут, а не успокоят. Комплект, который в принципе не может показать «нет», — не доказательство, а презентация.

## Процедура
1. **Назвать решение и его цену ошибки** (обратимое/необратимое, стоимость месяца ложного пути).
2. **Записать гипотезу в проверяемой форме** и что именно должно случиться с метрикой ([[M-brief-hypotheses]]).
3. **Определить, какие данные могли бы изменить решение:** по видам (прямое/косвенное/свидетельское/контекстное) — что докажет, что опровергнет.
4. **Собрать минимальный комплект:** начать с самых дешёвых независимых входов; для необратимых решений — заложить хотя бы один прямой вход.
5. **Проверить независимость входов:** разные методы, разные данные, разные выборки. Убрать дубли (два метода на одной базе = один вход).
6. **Зафиксировать критерий достаточности до сбора:** пороги, выборки, число входов, владелец решения.
7. **Собрать, свести комплект в таблицу:** вход → сила → что показывает → противоречия между входами.
8. **Разрешить противоречия:** сильный вход приоритетнее слабого; если противоречат два сильных — это новая исследовательская задача (разбирать механизм), а не повод выбрать удобный.
9. **Оформить вывод с уровнем уверенности:** «решение основано на …, уверенность высокая/средняя, остальные риски …» — в документ решения ([[M-six-pager]]).
10. **Зарезервировать пересмотр:** при каких новых данных вывод пересматривается (дата, триггер).

## Шаблон / чек-лист
| Поле | Заполнить |
|---|---|
| Решение и цена ошибки | |
| Гипотеза (проверяемая форма) | |
| Прямое доказательство | что измеряем, где взять |
| Косвенное/свидетельское/контекстное | вход, сила, что показывает |
| Критерий достаточности (до сбора) | пороги, выборки, число независимых входов |
| Противоречия между входами | как разрешены |
| Уровень уверенности и его границы | |
| Условия пересмотра вывода | новые данные, дата, триггер |

## Типичные ошибки
- Комплект из одних интервью на необратимое решение (все входы свидетельские и зависимые).
- Триангуляция дубликатами: «три опроса» на одной базе лояльных клиентов.
- Критерий достаточности задним числом: «данных уже достаточно, чтобы согласиться с моим мнением».
- Прокси-метрика, оторвавшаяся от целевой: рост кликов без роста платежей считается успехом.
- Подтверждающий поиск: дизайн исследования не допускает опровержения.
- Уверенность не названа: в документе решения не видно, на чём вывод и насколько ему верить.

## Вопросы, которые могут изменить решение
- Какое одно самое дешёвое наблюдение могло бы опровергнуть гипотезу — и сделано ли оно?
- Если самый сильный вход комплекта окажется ошибкой, решение изменится? Если да — комплект недостаточен.
- Какие входы независимы по-настоящему (данные, выборки, методы)?
- Какой уровень уверенности у нас и какой нужен для этого решения?
- Что должно произойти в мире, чтобы мы пересмотрели вывод?
